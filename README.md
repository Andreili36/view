## Отклонения от исходного задания

### 1. Создание GUI

- Пакет view вынесен в отдельный проект, подключаемый к centerDPO-Litvin как git submodule. При отсутствии папки view/ сборка ядра не ломается — приложение собирается как консольное, без WPF-зависимостей.

- Вместо набора отдельных форм — одна MainForm, реализованная по паттерну Singleton. Окно создаётся один раз и обслуживает всё приложение; переключение между экранами выполняется заменой содержимого, а не открытием новых окон.

- Дизайнер форм не используется — весь интерфейс строится программно на C# (без XAML). Это даёт полный контроль над иерархией элементов и упрощает версионирование.

- Форма авторизации и форма платформы реализованы как модули (AuthModule и PlatformModule), которые загружаются в хост-окно. Модули независимы и связаны через событие OnAuthorized.

- Ролевая модель видимости контента. Состав меню и доступные действия определяются декларативно через свойства секций (IsVisible, CanCreate, CanEdit, CanDelete). Меню и панель действий строятся автоматически, а не задаются вручную для каждой роли.

- Формы добавления студента, преподавателя и программы объединены в единый универсальный диалог CDPOFormDialog, параметризуемый списком полей. Отдельные формы под каждую сущность не создаются.

- Форма гостя как отдельное окно не создаётся. Роль «Гость» получает тот же PlatformModule, но с урезанным составом меню и действий — только раздел «Курсы» и только просмотр.

- Помимо CRUD-операций добавлена операция обновления данных, а таблица автоматически перечитывает данные после каждого действия (создание, изменение, удаление).

### 2. Реализация алгоритмов обработки данных

- Класс Controller не создаётся. Его роль распределена между AuthService (проверка учётных данных, обращение к БД) и AuthMain (UI и обработчики формы авторизации).

- Проверка логина и пароля выполняется через БД, а не через захардкоженный массив в коде. Учётные записи хранятся в таблице app_user, роль определяется по role_id.

- Метод isEmptyAccept не выделен в отдельный класс — проверка пустых полей встроена в метод авторизации сервиса.

- Связь формы авторизации с рабочей областью реализована через событие, а не через прямое создание следующей формы. Модуль авторизации не знает о модуле платформы.

### 3. Реализация графического интерфейса

- Форма администратора системы и форма добавления пользователя созданы без дизайнера — как классы, наследующие Window, с полностью программным построением интерфейса.

- Отдельная форма добавления пользователя системы не создаётся — она реализована как частный случай универсального диалога CDPOFormDialog с соответствующим набором полей.

- Управление внешним видом реализовано через собственный класс Theme, а не через стандартный Look and Feel. Палитра, шрифты и скругления заданы централизованно; все UI-компоненты берут значения из темы.

- Валидация данных выполняется на уровне формы ввода — при парсинге чисел и дат. При ошибке показывается диалоговое окно с понятным текстом, диалог остаётся открытым для исправления.

### 4. Разработка БД и импорт данных

- Схема БД дополнена полем registration_date в таблице студентов для учёта даты регистрации, что соответствует данным приложения.

- Таблица ролей заполняется вручную до импорта основных данных, так как на неё ссылаются пользователи через внешний ключ.

- Импорт выполняется через встроенный инструмент pgAdmin без использования внешних скриптов, что исключает необходимость в дополнительном ПО.

- Проверка схемы выполняется двумя контрольными запросами — на соединение пользователей с ролями и на подсчёт студентов по курсам. Это подтверждает корректность связей.

### 5. Организация подключения к БД

- Класс ConnectionDB не создаётся отдельно. Вместо него реализована универсальная обёртка DbWrapper с публичным контрактом из трёх методов (SqlQuery, SqlScalar, SqlExecute) и метода TestConnection.

- Обёртка вынесена за интерфейс IDbWrapper, что позволяет подменять её реализацию в модульных тестах без подключения к реальной БД.

- Параметры подключения вынесены во внешний файл app-config.json, который читается рядом с .exe. Смена сервера, базы или пароля не требует пересборки проекта.

- Проверка подключения выполняется до открытия GUI — в ViewLauncher перед созданием основного окна. При ошибке показывается сообщение и приложение завершается.

- Авторизация выполняется через БД — логин и пароль проверяются в таблице app_user параметризованным SQL-запросом. Роль пользователя определяется по role_id, полученному из БД.

- Строка подключения формируется программно из параметров конфига, а не задаётся жёстко в коде.

## Файл конфигурации БД — app-config.json

> [!IMPORTANT]
> Файл расположен рядом с исполняемым файлом .exe. Читается при запуске GUI-модуля в ViewLauncher. Позволяет менять параметры подключения без пересборки проекта.

### Структура файла:
```
{
  "database": {
    "host": "localhost",
    "port": 5432,
    "name": "dpo_litvin",
    "user": "user",
    "password": "pass"
  }
}
```

Описание параметров:

- `host` — Адрес сервера PostgreSQL. localhost — локальная машина, либо IP-адрес сервера `Строковый тип`
- `port` — Порт сервера PostgreSQL `Числовой тип`
- `name` — Имя базы данных `Строковый тип`
- `user` — Имя пользователя БД `Строковый тип`
- `password` — Пароль пользователя БД `Строковый тип`

> [!WARNING]
> Файл app-config.json исключён из системы контроля версий и не попадает в репозиторий — рядом с ним в проекте лежит образец app-config.example.json с фиктивными значениями. При развёртывании проекта на новой машине файл создаётся вручную из образца.
